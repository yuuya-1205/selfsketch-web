# PR とコミットの分割

## なぜ

このリポジトリは squash merge ではなく merge commit で main に入る。
巨大な PR やコミットが 1 個入ると、**問題が起きたときにその単位でしか戻せない**。
「画面3枚 + トークン変更 + CI 修正」が 1 コミットだと、CI 修正だけ残して画面を戻す、ができない。
分割は行儀の問題ではなく、リバートの粒度を確保するための実務要件。

## 大原則

| 単位 | 粒度 |
| --- | --- |
| PR | 1 スタック × 1 目的。レビューできる差分（目安 400 行以内） |
| コミット | それ単体でビルドが通り、単体でリバートできる最小単位 |
| ブランチ | `<type>/<主題>`（例: `feat/web-settings-tabs`） |

**着手前に分割計画を立てて、ユーザーに提示してから実装を始める。**
実装し終わってから「どう割るか」を考えるのは禁止。差分が絡み合って割れなくなる。

## PR の割り方

### 1. スタックをまたがない

`frontend/` `backend/` `analysis/frontend/` `analysis/backend/` は別 PR にする。
CI は 4 ジョブが独立しているので、1 スタックに閉じれば落ちた PR を単独で戻せる。

例外は「API 契約の変更を frontend と backend で同時に入れないと壊れる」ケースのみ。
その場合も本文に「この PR は 2 スタックにまたがる。理由: 〜」と明記する。

### 2. 目的をまぜない

1 PR に入れてよいのは次のうち **1 つだけ**。

- `feat` … 機能・画面の追加
- `fix` … バグ修正
- `refactor` … 振る舞いを変えない構造変更
- `chore` … ビルド・CI・依存・ツール設定
- `docs` … ドキュメントのみ
- `style` … フォーマットのみ（Prettier のバックログ解消など）

「ついでにリネームした」「ついでに lint 警告を消した」は別 PR に切り出す。

### 3. 依存する PR は積む（stacked PR）

土台 → 利用側の順に分け、後続 PR の本文に `Depends on #<番号>` を書く。
土台がマージされてから後続の base を main に付け替える。

```
#12 feat: 設定画面の共通レイアウトを追加       <- 土台
#13 feat: プライバシー設定画面を追加            <- Depends on #12
#14 feat: データと書き出し設定画面を追加        <- Depends on #12
```

### 4. 画面追加は「デザイン → 実装 → ドキュメント」で割らない

画面 1 枚は `.pen` ノード・実装・README 行がセットで初めて意味を持つ。
割るなら**画面ごと**（縦に割る）であって、工程ごと（横に割る）ではない。

## コミットの割り方

### 粒度

1 コミットは「レビュアーが 1 回で理解できて、単体で `git revert` できる」単位。
具体的には次を **別コミット** にする。

- 画面・機能の追加 … 1 画面 1 コミット
- 共通コンポーネント / トークンの追加・変更 … それを使う画面とは別
- モックデータ・型の追加 … 使う側とは別にしてよい（1 コミットに収まるなら同じでよい）
- 既存ファイルの移動・リネーム … 中身の変更とは必ず別
- 自動整形（`prettier --write` / `gofmt` / `ruff format`）… 手で書いた変更とは必ず別
- 依存の追加・更新 … 常に単独
- ドキュメント（README / AGENTS.md）… まとめて 1 コミットでよい

### 各コミットで CI が通ること

`git rebase` や `git revert` の途中で壊れないように、コミット単位でチェックを通す。
最低限、そのスタックの typecheck / build が通る状態でコミットする。

```bash
cd frontend && npm run typecheck && npm run build
cd backend && go build ./... && go vet ./...
cd analysis/frontend && npm run typecheck && npm run build
cd analysis/backend && ruff check . && python -m pytest
```

### メッセージ

`<type>: <日本語の要約>` の Conventional Commits。既存の履歴に揃える。

```
feat: プライバシー設定画面を実装する
refactor: コンポーネントと非コンポーネントの export を分離する
chore: lint / フォーマッタ / テストを導入し CI に組み込む
```

- 要約は現在形・体言止めか「〜する」。80 文字以内
- 「なぜ」が自明でないときだけ本文を足す。「何を」は diff を見ればわかるので書かない
- 1 コミットに複数の type が混ざったら、それは割り忘れ

## スタック別の注意

| スタック | 単独でコミットを割るべきもの |
| --- | --- |
| `frontend` | `packages/ui` への追加は `apps/*` の利用側と別コミット。`.prettierignore` のバックログ解消は整形コミット単独（AGENTS.md 参照） |
| `backend` | ハンドラ追加とルーティング登録は同じコミットでよい。`go.mod` の更新は単独 |
| `analysis/frontend` | `frontend/` とは完全に別プロジェクト。同じ PR に混ぜない |
| `analysis/backend` | `requirements.txt` と `requirements-dev.txt` の更新は単独 |

## 手順

1. 着手前に、触るスタックと目的を数えて **PR とコミットの分割計画を書き出し、ユーザーに見せる**
2. PR ごとにブランチを切る（`git switch -c feat/...`）
3. 計画したコミット単位で `git add -p` して commit。1 コミットごとに typecheck / build
4. push して `gh pr create`。本文に目的・スクリーンショット・依存 PR を書く
5. 次の PR は前の PR がマージされてから main を取り込んで始める

## やってはいけない

- 実装を全部終えてから `git add -A && git commit` で 1 個にまとめる
- 「レビューしやすいように」と言いながら 1 ファイル 1 コミットに刻む（意味の単位で割る）
- 整形と実装を同じコミットに入れる（diff がノイズだらけになりレビューできない）
- main に直接コミットする
