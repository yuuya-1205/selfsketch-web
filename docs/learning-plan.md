# 学習計画

このリポジトリは、2026-09-17 に全消去して作り直した SelfSketch の Web アプリです。
作り直しの目的は「アプリを完成させること」ではなく、以下の技術を **1 本のアプリを通して学ぶこと** に置きます。

## 学びたいこと

- TDD と AI 駆動開発で作る。開発手順そのものを学ぶ対象にする
- Next.js で Web フロントエンドを書く。UI から始めて E2E まで通す
- Go でバックエンドを書く
- RDB（PostgreSQL）の設計と運用
- インフラ全般。特に AWS と Docker。慣れたら Kubernetes（EKS）まで
- Python でデータ分析ができるようになる
- テスト設計書、内部設計書、クラス図などの設計ドキュメントを書けるようになる
- CI/CD を自分で組めるようになる。GitHub Actions でテストを回し、AWS へ配置するまで
- セキュリティ。認証を作りながら、守るべきものと守り方を学ぶ
- 可観測性。本番で何が起きているか分かる状態を作る
- 計測とイベント設計。分析に使うデータをアプリ側で意図して記録する
- LLM の組み込み。アプリの中核にある AI 伴走を自分で実装する
- アクセシビリティ。UI の質とテストの質を同時に上げる
- 市場価値の高い技術を学び、今後も続く学習習慣をつける

これらは 1 つの構成にそのまま収まります。

```
Next.js（画面） → API 契約（OpenAPI） → Go（API） → PostgreSQL
        └── Docker Compose でローカル起動
        └── AWS に配置
        └── たまった実データ（イベント）を Python で分析
        └── 振り返りは LLM API に問い合わせる（フェーズ 5）
```

## 開発の仕方

### TDD

- 失敗するテストを書いてから実装する。テストのない実装は入れない
- 単体・コンポーネントは Vitest と Testing Library、E2E は Playwright
- API との境界は契約（OpenAPI）で固定し、フロントは契約に対してテストする
- 契約を先に決めておくことで、裏側を仮 API から Go に差し替えても **E2E テストは書き換えない**

### AI 駆動開発

- 仕様 → 失敗するテスト → 実装 → 検証、の順を AI にも守らせる。AGENTS.md に手順として書く
- 人が見るのはまずテスト。テストが仕様を正しく表しているかを確認してから実装に進む
- 繰り返す作業はスキルに切り出す（画面の追加、エンドポイントの追加、検証手順など）
- AI に何を任せて何を自分で書くかも、学習ログに残す

### 自分で書く段階と AI に任せる段階

一度も自分で書いたことのないものは、AI が書いたものの良し悪しを判断できない。
だから **技術ごとに 3 段階** で AI の関わり方を変える。段階を上げる判断は自分で宣言し、学習ログに一行残す。

| 段階 | 自分の役割 | AI の役割 | 目安 |
| --- | --- | --- | --- |
| 1. 自分で書く | 最初の 1 つを自分の手で書く | コードを書かない。選択肢を出す、質問に答える、書いたものをレビューする | その技術で初めて書くもの |
| 2. AI が下書き | 下書きをレビューして直す | 下書きを書き、直された点から学ぶ | 自分で書いたものと比べて良し悪しが分かるようになったら |
| 3. AI に任せる | テストと設計のレビューに集中する | 実装まで書く | 下書きに直す点がほぼ無くなったら |

- 「最初の 1 つ」の例: 最初の画面、最初のコンポーネントテスト、最初の E2E、最初のマイグレーション、
  最初の Go ハンドラ、最初の GitHub Actions ワークフロー、最初の Terraform
- 段階は技術ごとに別。Next.js は段階 3 でも Go は段階 1、という状態は普通に起きる
- どの段階でも、テストが仕様を表しているかのレビューは自分でやる（変えない）
- フェーズ 1 と 2 は段階 1 の作業が多いので時間が伸びる。見積もりはそれを織り込む

## テストを深く学ぶ

テストはこの計画で一番深さを出す領域にする。使い方を覚える学習ではなく設計判断の連続なので、
深く学ぶと全フェーズに効く。

### 学び方

- 項目ごとに **「どうするのがベストプラクティスか」を一緒に考えてから決める**。答えを写さない
- 考えた結論と、そう決めた理由、採らなかった選択肢を `docs/` の学習ログに残す
- AI に書かせたテストは必ず自分がレビューする。「仕様を表しているか」「実装の詳細に依存していないか」を毎回判断する。
  AI 駆動開発では実装より先にテストが目に入るので、これがテストを深く学ぶ一番の近道になる

### フェーズ 0 と 1（フロント）で学ぶこと

- **何をテストし、何をしないか。** 実装の詳細ではなく振る舞いを検証する。Testing Library の
  「ユーザーが見えるものでクエリする」思想を教材にする
- **テストピラミッドの現実。** コンポーネントテストと E2E の配分。E2E は主要導線だけに絞り、
  細かい分岐はコンポーネントテストで持つ判断を実地でやる
- **テストダブルの使い分け。** スタブ、モック、フェイクの違い。フェーズ 1 の仮 API はフェイクの典型例で、
  なぜ MSW のモックより契約に沿ったフェイクを選ぶのかを考える
- **E2E の壊れにくさ。** テスト ID の方針、データの用意と後片付け、並列実行、フレーキーテストの潰し方
- **TDD の 2 流派。** 内側から作る古典派と、外側から作りモックで境界を決めるロンドン派。
  UI から E2E まで通す進め方は後者に近いので、意識して使い分ける

### フェーズ 2（Go と RDB）で学ぶこと

- **Go の table-driven test** と、テストを仕様書として読める書き方
- **DB を含むテスト。** testcontainers で本物の PostgreSQL を立てるか、トランザクションで巻き戻すか。
  モックせずに本物を使う判断基準
- **契約テスト。** OpenAPI に対してフロントと Go の両方を検証し、契約が壊れたら CI で落とす。
  フェーズ 2 の完了条件「E2E を書き換えずに差し替わる」を保証する仕組み

### 横断で、余裕が出てから

- **テストの質を測る。** カバレッジの限界と、ミューテーションテストで「テストが本当に落ちるか」を確かめる
- **プロパティベーステスト。** 日付や境界値など、具体例を列挙しきれない部分に効く。
  前回タイムゾーン依存で CI だけ落とした経験を題材にする

## 設計ドキュメントを書けるようになる

テスト設計書、内部設計書、クラス図などを、実装の前に自分で書けるようになる。
「仕様 → 設計 → テスト設計 → テスト → 実装」の順に組み込み、設計ドキュメントを TDD の入口にする。

### 方針

- **書く前に読み手と目的を決める。** 誰が何を判断するための文書かを 1 行目に書く。目的のない文書は書かない
- **1 機能ぶんを小さく書く。** 全体を一気に書かず、フェーズ 1 の導線 1 本、画面 1 枚、テーブル 1 群のように、
  実装の単位と同じ粒度で書いて実装と一緒に PR に入れる
- **図は Mermaid で書く。** Markdown に埋め込め、GitHub 上で描画され、差分がレビューできる。
  ツールを覚えるより「何を図にすべきか」に時間を使う
- **コードと一緒に更新する。** 実装が変わったら同じ PR で文書も直す。追従できない文書は削る
- **AI が下書きし、自分がレビューして直す。** テストと同じく、まず自分の目で「設計として正しいか」を判断する訓練にする
- 置き場は `docs/design/`。1 文書 1 ファイル、フェーズやドメインで分ける

### 何を、いつ書くか

| 文書 | 何を書くか | 書くフェーズ |
| --- | --- | --- |
| テスト設計書（観点表） | 画面や API ごとの入力・状態・期待結果の一覧。ここからコンポーネントテストと E2E を起こす | 1 から |
| 画面仕様 | 画面ごとの表示項目、操作、遷移、状態（読込 / 空 / エラー）。.pen を読んで文章にする | 1 から |
| シーケンス図 | 導線 1 本ぶんの画面・仮 API・認証のやりとり。後で Go に差し替わっても図は変わらないことを確認する | 1 |
| 外部設計（API 契約） | OpenAPI そのもの。エンドポイント、リクエスト・レスポンス、エラー形式 | 1 |
| ER 図 | テーブル、キー、関連。契約から逆算して作る | 2 |
| 内部設計書 | Go の層構成（handler / usecase / repository）、依存の向き、エラーの流し方、トランザクション境界 | 2 |
| クラス図 | Go の struct と interface の関係。何を interface にして何を差し替え可能にしたかを説明する図 | 2 |
| 構成図 | AWS 上のコンポーネントと通信経路、費用が乗る箱 | 3 |

### 学ぶうえでの注意

- 設計文書と TDD は対立しない。設計文書を「実装前に考えたことの記録」に留め、詳細はテストとコードに任せる
- 書きすぎの兆候は「実装後に一度も読み返さない文書」。次から省く
- クラス図は Go にはクラスが無いので、struct と interface の依存図として描く。継承ではなく合成と interface を表現する練習になる

## CI/CD を組めるようになる

CI は「テストのない実装は入れない」という規約を機械的に守らせる装置として使う。
フェーズごとに 1 段ずつ育てていき、最後は AWS への配置（CD）まで自動化する。

### 方針

- **最初から全部組まない。** そのフェーズで守りたいことだけをチェックに足す
- **速く保つ。** 1 回の実行は 5 分以内を目標にし、超えたらジョブ分割やキャッシュで直す。遅い CI は無視されるようになる
- **ローカルで同じコマンドが動く。** CI 専用の手順を作らず、`npm test` や `go test` をそのまま呼ぶ。CI だけで落ちる差（タイムゾーン、環境変数、ロケール）は前回の失敗そのものなので、意識して潰す
- **main は必ず緑。** ブランチ保護で必須チェックを設定し、赤のままマージできないようにする
- **秘密情報を CI に長期間置かない。** AWS へは OIDC で一時的な権限を取り、アクセスキーを Secrets に置かない

### 何を、いつ学ぶか

| フェーズ | CI に足すもの | 学ぶこと |
| --- | --- | --- |
| 0 | lint、型チェック、コンポーネントテスト、ブランチ保護 | GitHub Actions の基本構造（trigger / job / step）、依存のキャッシュ、必須チェック |
| 1 | Playwright の E2E、失敗時のスクリーンショットとトレースの保存、`TZ=UTC` での実行 | ブラウザを CI で動かす、artifact の扱い、フレーキーテストの検出と再試行の判断 |
| 2 | Go のテスト、PostgreSQL の service container、OpenAPI 契約の検証、Docker イメージのビルド | 複数ジョブの並列化と依存関係、DB を CI で立てる、契約が壊れたら落とす仕組み、ビルドキャッシュ |
| 3 | main マージで AWS へ配置する CD、Terraform の plan を PR に貼り apply は main で | OIDC での認証、環境（staging / production）の分け方、ロールバックの手順、配置の失敗を検知する |
| 4 | ノートブックの出力を除いてコミットさせるチェック | 分析コードもレビューできる形に保つ |

### 学ぶうえでの注意

- CI の学習ログには「なぜそのチェックを足したか」を書く。チェックが増えるほど遅くなるので、理由の無いチェックは足さない
- CI で落ちたときは、ローカルで再現してから直す。CI 上で試行錯誤して push を繰り返すのは避ける
- フェーズ 3 の CD は料金と事故が伴うので、まず staging だけに自動配置し、production は手動承認を挟む

## 追加で学ぶこと

計画を立てたあとに足した 5 項目。それぞれ既存のフェーズに寄せて、新しいことを同時に増やさないようにする。

### セキュリティ（フェーズ 1 と 2）

日記や感情のデータを扱うアプリなので、漏れたときの被害が大きい。JTBD にも「データが流出したら弱さが晒される」という不安がある。
認証を作るフェーズ 1 で一緒に学ぶのが自然。

- セッションと JWT の選択と、その理由。Cookie の属性（HttpOnly / Secure / SameSite）
- CSRF と XSS の仕組みと、Next.js と Go それぞれでの防ぎ方
- パスワードの保存（ハッシュ化のアルゴリズムとコスト）、パスワード再設定トークンの扱い
- レート制限、ログインの試行回数制限
- 秘密情報の管理。リポジトリに置かない、環境ごとに分ける、ローテーションできる形にする
- 依存パッケージの脆弱性チェックを CI に足す（フェーズ 0 から）
- フェーズ 2 で SQL インジェクションと認可（自分のデータしか見えない）をテストで保証する

### 可観測性（フェーズ 3）

AWS に置いた瞬間に「動いているか分からない」状態になる。配置と同時に見える状態を作る。

- 構造化ログ（JSON）と、リクエストを追跡する ID の付け方
- メトリクス。リクエスト数、エラー率、遅延、DB 接続数
- アラート。何が起きたら通知するか、何は通知しないか
- エラー追跡。スタックトレースをユーザーの操作と結びつけて見る
- 構成図に「どこでログとメトリクスを集めるか」を描き加える

### 計測とイベント設計（フェーズ 1 で設計、2 で保存、4 で分析）

Python で分析するデータは、アプリ側で「何を記録するか」を先に決めないと存在しない。
KPI（7 日継続率、月間アクティブ、振り返り投稿数）から逆算して設計する。

- KPI ごとに「どのイベントがいつ記録されれば計算できるか」を表にする
- イベント名の命名規則、共通属性（ユーザー、時刻、画面）、個別属性を決める
- 個人情報や日記本文をイベントに入れない。分析に必要な最小の属性にする
- フェーズ 2 でイベントのテーブルを設計し、フェーズ 4 でそのテーブルから KPI を出す

### LLM の組み込み（フェーズ 5、新しいもの: LLM API）

Lean Canvas の解決策に「AI 伴走の振り返り」、オンボーディングに「AI Future Self」がある。アプリの中核だが、
フェーズ 1 の 6 画面には AI が要る画面が無いので、最後に置いても順序に無理がない。

- プロンプトの設計と、日本語での応答品質の見方
- ストリーミング応答を Go から Next.js まで通す
- コストと遅延の管理。トークン数の見積もり、キャッシュ、タイムアウト
- 出力の評価とテスト。決定的でない出力をどうテストするか（構造の検証、評価用データセット、LLM による採点）
- 失敗時の振る舞い。API が落ちたときにアプリとしてどう見せるか
- ユーザーの日記を LLM に渡すときのプライバシー。何を送り、何を送らないか。セキュリティの項目とつなげる

完了条件: 「今日のリフレクション」画面で、日記の内容に応じた振り返りの返答がストリーミングで表示され、
その品質を評価するテストが CI で回る。

### アクセシビリティ（フェーズ 1 から、テスト設計の観点として）

Testing Library の「ユーザーが見えるものでクエリする」思想と一致するので、追加コストが小さい。

- 画面ごとのテスト設計書に、キーボード操作、フォーカスの順序、ラベルと役割、コントラストの観点を足す
- Playwright に自動チェック（axe）を組み込み、E2E と同時に流す
- .pen のデザインに無い状態（フォーカスリング、スクリーンリーダー向けの文言）は画面仕様で決める

## 進め方の原則

- **同時に新しいことを 2 つ以上始めない。** フェーズごとに「新しい技術」を 1 つに絞る
- **1 機能を縦に貫通させて終わらせる。** 画面だけ、API だけを大量に作らない
- **終わりが見える単位で区切る。** 各フェーズに完了条件を置き、終わったら次へ進む
- PR とコミットは細かく分ける。1 コミットは単体でビルドが通り、単体で revert できる最小単位
- 学んだことは `docs/` に残す。フェーズごとに学習ログを書く

## フェーズ

### 0. 土台と習慣づくり（新しいもの: TDD と AI 駆動の手順）

- Next.js の雛形に Vitest、Testing Library、Playwright を入れる
- AGENTS.md に TDD の手順と規約を書く。CI で lint、型チェック、テストを回し、ブランチ保護で必須にする
- 依存パッケージの脆弱性チェックを CI に足す
- 学習リズム（週 30 時間、週 2〜3 PR）を決める。学習ログは `docs/log/` に週 1 ファイル（決定済み）
- `docs/design/` の雛形（テスト設計書、画面仕様）を 1 枚ずつ作り、Mermaid が GitHub で描画されることを確認する

完了条件: 空の画面 1 つに対してコンポーネントテストと E2E が CI で緑になる。

### 1. UI から E2E まで（新しいもの: Next.js App Router）

- 題材に沿って API の契約（OpenAPI）を先に書く
- 契約どおりの固定データを返す仮 API を Next.js の Route Handler で置く
- App Router と Server Components で画面を作り、画面ごとにコンポーネントテストと E2E を書く
- 認証もこのフェーズで入れる
- 画面ごとに画面仕様とテスト設計書を書いてからテストを起こす。導線 1 本のシーケンス図を書く
- CI に Playwright の E2E を足し、失敗時のスクリーンショットとトレースを残す
- 認証と一緒にセキュリティ（セッション、Cookie、CSRF、パスワード保存、レート制限）を学ぶ
- KPI から逆算してイベント設計を書く。テスト設計書にアクセシビリティの観点を足し、axe を E2E に組み込む

対象画面は `selfsketch.pen` の Web 版から次の 6 枚に絞る。
「ログインして習慣を作り、今日の画面に出て、詳細を見る」の 1 本の導線で E2E が書け、API 契約もこの範囲で足りる。

| 区分 | 画面 | .pen のノード |
| --- | --- | --- |
| 認証 | W-Auth 1 ログイン | `ES2YF` |
| 認証 | W-Auth 2 サインアップ | `wM8qs` |
| 認証 | W-Auth 3 パスワード再設定 | `b8yrP` |
| 今日 / 習慣 | W-Home 1 今日ダッシュボード | `fUv9W` |
| 今日 / 習慣 | W-Home 2 習慣を作成（Modal） | `KOgk7` |
| 今日 / 習慣 | W-Home 3 習慣詳細 | `QMnku` |

完了条件: 上の 6 画面が仮 API の上で動き、導線を通す E2E が通る。

この 6 画面が終わったら、以降は **画面を少しずつ足す** 形で進める。1 画面 1 PR を目安に、
残りの Web 版 38 画面（ストリーク、ジャーナル、ギャラリー、未来の自分、インサイト、ソーシャル、通知と設定、
プレミアム、リフレクション、レスポンシブ、エラーと空状態）から導線のつながる順に選ぶ。
フェーズ 2 以降と並行して足してよい。

### 2. Go と RDB（新しいもの: RDB 設計。Docker もここで入る）

- Docker Compose で PostgreSQL を立てる
- 契約から逆算してテーブルを設計し、マイグレーションを書く
- Go で契約を実装し、仮 API を差し替える。Go 側も TDD で書く
- 実装前に ER 図、内部設計書、struct と interface のクラス図を書く
- CI に Go のテスト、PostgreSQL の service container、契約の検証、Docker ビルドを足す
- イベントのテーブルを設計する。SQL インジェクションと認可をテストで保証する

完了条件: フェーズ 1 の E2E テストを書き換えずに、裏が Go と PostgreSQL に切り替わっている。

### 3. AWS（新しいもの: クラウド配置）

- Docker 化したものを AWS に配置する
- まず ECS Fargate か App Runner と RDS。慣れたら Terraform で書き直す
- 配置前に構成図を書き、費用が乗る箱を明示する
- main へのマージで staging に自動配置する CD を組む。AWS への認証は OIDC。production は手動承認を挟む
- 構造化ログ、メトリクス、アラート、エラー追跡を配置と同時に入れる
- 料金が発生する唯一のフェーズ。予算は **月 2 万円まで**（フェーズ 6 で Kubernetes に入ったら月 5 万円まで）。
  RDS と Fargate の最小構成なら収まる見込みだが、着手時に見積もりを出して確認する

完了条件: 公開 URL からアプリが使え、main へのマージだけで staging が更新され、エラーが起きたら通知が届く。

### 4. Python でデータ分析（新しいもの: pandas / Jupyter）

- アプリの DB にたまった実データを pandas と Jupyter で読む
- 「自分のデータ」なので学習題材として続きやすい
- フェーズ 1 で設計したイベントから KPI（7 日継続率、月間アクティブ、振り返り投稿数）を出す

完了条件: イベントのテーブルから KPI を出す分析ノートブックを 1 つ書く。

### 5. LLM の組み込み（新しいもの: LLM API）

- 「今日のリフレクション」画面に AI 伴走の返答を組み込む
- Go から Next.js までストリーミングを通し、コストと遅延、失敗時の振る舞いを設計する
- 決定的でない出力のテスト方法を学び、評価を CI に組み込む

完了条件: 日記の内容に応じた返答がストリーミングで表示され、品質を評価するテストが CI で回る。

### 6. Kubernetes への移行（新しいもの: Kubernetes / EKS）

- フェーズ 3 で ECS Fargate に置いたものを EKS に移す。「なぜ Kubernetes か」を移行の中で説明できるようになる
- まずローカルの kind で Deployment、Service、Ingress、ConfigMap と Secret、ヘルスチェックを触る。ここまでは費用ゼロ
- その後 EKS に上げ、Terraform でクラスタを書き、CD を EKS 向けに組み替える。可観測性も Kubernetes 流に載せ替える
- 費用は EKS のコントロールプレーンだけで月 1 万円強かかる。このフェーズの予算上限は月 5 万円
- 市場価値のために入れる項目なので、アプリに必要かどうかではなく「自分で説明できるか」を完了の基準にする

完了条件: staging が EKS 上で動き、main へのマージで更新され、ECS との違いを構成図と文章で説明できる。

## 決めたこと

- **アプリの題材。** `selfsketch.pen` 内の Lean Canvas と JTBD に定義がある。20〜35 歳で自分を見失いがちな人向けに、
  毎日 5 分「描く・書く」で内省する習慣アプリ。独自価値は「自分を責めずに今日を残す」。
  KPI は 7 日継続率、月間アクティブ、振り返り投稿数。Python で分析する対象もここから決める
- **デザインの元。** `~/Desktop/selfsketch.pen`（Pencil）。Web 版 44 画面と管理コンソール 10 画面、shadcn 系のデザインシステムがある。
  実装前に該当画面を Pencil MCP で読む
- **AWS の予算。** フェーズ 3〜5 は月 2 万円まで。フェーズ 6（Kubernetes）に入ったら月 5 万円まで
- **確保できる時間。** 週 30 時間。全体で約 4〜5 か月、2027 年 2 月末に完了する見込み
- **学習ログの置き場。** `docs/log/` に週 1 ファイル、月曜日の日付で命名。書き方は `docs/log/README.md`
- **リポジトリの分け方。** Web とバックエンドはこのリポジトリに同居させる。将来のスマホアプリ（Flutter を想定、着手はかなり先）は別リポジトリにする。
  バックエンドはあとから切り出せる形で置く。守ることは 3 つ。
  OpenAPI の契約はリポジトリ直下の `api/` に置いてバックエンドの持ち物にし、Next.js の仮 API も Go もそこを読む。
  `backend/` は自前の `go.mod`、Dockerfile、CI ジョブを持ち、フロントのファイルを参照しない。
  契約の後方互換を壊す変更の扱いをフェーズ 2 で決める
