## 決めたことと理由

- **フロント先行で UI から E2E まで通し、その後 Go と RDB**。TDD の見返り（契約を軸に裏を差し替える）が見えやすい。採らなかったのは RDB と Go 先行
- **フェーズ 1 は 6 画面**（認証 3、今日/習慣 3）。1 本の導線で E2E が書け、契約もこの範囲で足りる。44 画面全部は学習の題材として多すぎる
- **単一の Next.js リポジトリで開始**。いま必要なのはフロントだけ。`frontend/` への掘り直しはフェーズ 2 で行い、それ自体を学びにする。採らなかったのは最初からモノレポ
- **`src/` ディレクトリあり**。設定とソースが分かれて見通しがよい
- **npm**。前回と同じで新しい道具を増やさない。採らなかったのは pnpm（速いが新しいことが 1 つ増える）
- **DOM は jsdom**。標準的で情報が多い。採らなかったのは happy-dom（速い）
- **テストはコンポーネントの隣に置く**。仕様として読むとき対象と同じ場所にあるほうが読みやすい。採らなかったのは `__tests__/` にまとめる方式
- **`vite-tsconfig-paths` は入れない**。Vite 8 が `resolve.tsconfigPaths` で標準解決できる
- **Web とバックエンドは同居、将来の Flutter は別リポジトリ**。契約は `api/` に置きバックエンドの持ち物にする
- **学習ログは `docs/log/` に週 1 ファイル**。理由は `docs/log/README.md`
- **フロントはクリーンアーキテクチャの 3 層（domain / data / presentation）**。Flutter と同じ語彙で考えられる。DTO と Repository を data に置き、DTO は契約から生成、Mapper は形が同じでも置く。採らなかったのは 4 層（application を独立）と層別フォルダー
- **ユースケースは最初は置かない**。2 つ以上の Repository をまたぐか、呼ぶだけではないテストが書けるときに domain の `usecases/` に切り出す。業務ルールは domain の純粋関数に置き hooks には書かない。採らなかったのは最初からユースケース層を置く方式
- **Playwright は Chromium のみ、E2E は `e2e/` に集約**。E2E は画面をまたぐのでコンポーネントの隣には置けない。CI では 2 回まで再試行しトレースを残す

## 学んだこと

- create-next-app はテストランナーを一切入れない。`test` スクリプトも無い。Next.js は「テストは選んで入れる」立場
- `tsc --noEmit` は Next.js がビルド時に生成する `.next/types/` のグローバル型（`LayoutProps` など）に依存する。ビルド前に走らせると落ちる。CI では `next build` か `next typegen` を先に
- Vitest 5 は `@types/node` に `^22` を要求する。雛形の `^20` と衝突したので 22 に上げた。`--force` で握りつぶさず、要求に合わせて直す
- Testing Library は `getByRole("heading", { level: 1 })` のように**ユーザーが認識する役割で要素を探す**。クラス名や DOM 構造に依存しないので、見た目を変えてもテストが壊れない。0 件でも 2 件以上でも失敗するので「ちょうど 1 つ」も同時に検証している
- テストは通ることだけでなく、**わざと壊して落ちることも確認する**。落ちないテストは何も守っていない
- 学習ログは PR ごとに追記する。まとめて書こうとすると書かなくなる
- コンポーネントテストは「描画される」まで、E2E は「本物のブラウザで開いて見える」まで検証する。同じ見出しを両方で確認しているが、確認している範囲が違う
- Vitest の対象から `e2e/` を除外しないと、Playwright のテストを Vitest が拾って壊れる。ランナーが 2 つあるときは守備範囲を分ける

## 宿題

- [ ] **ユースケースと単一責務の関係を自分の言葉で図解する。** hooks の責務は「画面の状態と操作」、複数の Repository を順に呼んで結果を組み合わせる「業務の流れ」は別の責務。2 つ目の Repository が出た瞬間に hooks が 2 つの責務を持つので、そこでユースケースに切り出す。逆に Repository が 1 つのときにユースケースを作ると「hooks が呼ぶ、ユースケースが呼ぶ、Repository が呼ぶ」と同じことを 3 回書くだけで、責務は分かれていても中身が無い。単一責務は「分けるほど良い」ではなく「責務が本当に 2 つあるときに分ける」。これを図にして、`docs/design/architecture.md` の「採らなかった選択肢」から参照する
