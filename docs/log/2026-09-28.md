## 決めたことと理由

- **「または」はテストしない**
  理由：守っている仕様がほとんどないため、なくてもユーザーは困らないと判断した為。

- **期待結果はレイヤー名ではなく、役割と名前で書く**
  理由：ユーザーにとって大事なものは「ボタンである」「リンクである」「ラベルの付いた入力欄である」という役割と、そこに書かれた名前のため。

- **伏せ字は type="password"**
  理由：<input type="password">にしておけばブラウザが自動で伏せ字にするため。

- **フェーズ 1（フロント）でもブロック図、内部設計書、クラス図を書く**
  理由：今後の大規模開発に備えて、設計資料を書くことに慣れておきたいため。計画ではフェーズ 2（Go）からだったが、前倒しした。
  時間が 10〜20 時間ほど増えるのは構わないと判断した。
  採らなかった選択肢：フロントでは書かない（元の計画）。軽い構成メモを 1 枚だけにする。

- **CIに脆弱性チェックを追加する**
  理由：package.json に書いた依存は 18 個だが、依存の依存まで含めると約 540 個入っていて、そのどれかにあとから穴が見つかる。
  手で `npm audit` を毎回実行するのは忘れるので、依存が入ってくる入口である PR で必ず調べ、穴がある状態で main に入らないようにする。

- **今の job（test）に `npm audit` のステップを 1 つ足す**
  理由：1 行で済み、CI の流れがそのまま読める。一度に足すのは 1 段にしたい。
  採らなかった選択肢：定期実行の別ワークフロー（cron と job 分けで新しい要素が 2 つ増える）。Dependabot（CI のステップではなく、PR が勝手に増える）。
  dependency-review-action（PR で新しく足した依存しか見ないので、今ある依存の穴を見逃す）。

- **`--audit-level=high` で、high 以上のときだけ落とす**
  理由：low や moderate まで落とすと、直せない軽いもので止まりやすい。
  採らなかった選択肢：オプションなし（low 以上で落ちる）。

- **dev 依存も含めて調べる**
  理由：Vitest や Playwright も CI と自分のマシンで実際に動くため。
  採らなかった選択肢：`--omit=dev`（本番に載る依存だけを調べる）。

- **`npm ci` の後ろに置く**
  理由：「インストール → 調べる」の順に読める。
  採らなかった選択肢：`npm ci` の前に置く（`npm audit` は package-lock.json だけ見るので前でも動き、早く落ちる）。

- **コミットの種別は Conventional Commits に合わせる（feat fix docs test refactor ci chore）**
  理由：これまでの履歴で `feat` と `feature` が混ざっていて、どちらを使うか毎回迷っていた。世の中で使われている形に揃えれば迷わない。
  採らなかった選択肢：今の種別（`feature`、`add` など）をそのまま正式にする。`test(login):` のように対象範囲も書く（範囲の名前を決める手間に見合わない）。

- **test は「テストだけを変えたとき」、refactor は「振る舞いもテストも変えず、緑のまま」のときに使う**
  理由：テストと実装を一緒にコミットすると決めたので、そのコミットは feat か fix になる。test の意味を狭くしないと矛盾する。
  refactor に条件を書いておけば、AI がリファクタのついでに振る舞いを変えたときに違反だと分かる。

- **1 つの目的で 1 コミットにする**
  理由：一部だけ戻したいときに戻せるようにするため。作業の区切りでまとめると、件名が「〜など」になり、何を戻すのか分からなくなる。
  採らなかった選択肢：作業の区切り（休憩前、1 日の終わり）で 1 コミット。ファイルごとに 1 コミット（1 つの変更が複数のファイルにまたがると、途中のコミットが壊れた状態になる）。

- **テストが通った時点で、テストと実装を 1 コミットにする。リファクタは別のコミットにする。赤は確かめるが、コミットには残さない**
  理由：赤のたびにコミットしていたらキリがない。ただし赤を確かめること自体はやめない。テストが本当に落ちる力を持っているかを確かめるため。
  採らなかった選択肢：赤・緑・リファクタをすべて別のコミットにする（TDD の証拠は残るが、赤のコミットはテストが落ちる状態で、そのコミット単体では動かない）。
  区切らずに 1 コミットにする（振る舞いの変更とリファクタが混ざり、レビューも取り消しもしにくい）。
  赤を確かめるのもやめる（落ちないテストに気づけない）。

- **保留にしたこと**
  件名の文体（動詞の言い切りにするか）、単独のコミットにするもの（自動整形、学習ログなど）は、困ったときに AGENTS.md に足す。
  赤を確かめた記録の残し方は、PR テンプレートにチェック欄を置く案が有力。PR の節を決めるときに決める。

- **AGENTS.md の PR の節（大きさ、テンプレート）は後回しにし、フェーズ 0 を閉じる**
  理由：AGENTS.md は最小限で書き、困ったら足す方針。PR の形は、フェーズ 1 で最初の PR を出すときに実物を見ながら決めたほうが具体的になる。
  採らなかった選択肢：PR の節を書き終えてからフェーズ 0 を閉じる。

## 学んだこと

- `npm audit` の「1 critical severity vulnerability」は件数の報告で、終了コードとは別物。CI が見ているのは終了コード（0 が成功、それ以外が失敗）だけ。
  終了コードは画面に出ないので `echo $?` で見る
- `npm audit --help` は使い方を表示するだけなので、終了コードは 0 になる。調べていないのに緑になる
- 緑になることだけでなく、赤になることも確かめる。脆弱性のある古いパッケージ（lodash 4.17.4）を一時的に入れて、終了コードが 1 になるのを見た
- 脆弱性には 2 種類の学びがある。個々の穴の中身（XSS、Prototype Pollution など）はセキュリティの学習。
  他人のコードの穴をどう管理するか（依存関係の管理、サプライチェーンセキュリティ）は運用の学習で、今回の CI はこちら
- AGENTS.md は、AI が作業を始めるたびに毎回自動で読み込まれる。だから最小限にして、困ったら 1 行ずつ足す
- `chore` は、アプリの振る舞い、テスト、ドキュメントのどれにも当たらない雑務（`.gitignore`、`package.json` の scripts、エディタの設定など）
- `fix` は「不具合を直す」で、修正全般ではない。ドキュメントの誤字を直すのは `docs`、テストの期待値を直すのは `test`
