## 決めたことと理由

- **「または」はテストしない**
  理由：守っている仕様がほとんどないため、なくてもユーザーは困らないと判断した為。

- **期待結果はレイヤー名ではなく、役割と名前で書く**
  理由：ユーザーにとって大事なものは「ボタンである」「リンクである」「ラベルの付いた入力欄である」という役割と、そこに書かれた名前のため。

- **伏せ字は type="password"**
  理由：<input type="password">にしておけばブラウザが自動で伏せ字にするため。

- **フェーズ 1（フロント）でもブロック図、内部設計書、クラス図を書く**
  理由：今後の大規模開発に備えて、設計資料を書くことに慣れておきたいため。計画ではフェーズ 2（Go）からだったが、前倒しした。
  時間が 10〜20 時間ほど増えるのは構わないと判断した。
  採らなかった選択肢：フロントでは書かない（元の計画）。軽い構成メモを 1 枚だけにする。

- **CIに脆弱性チェックを追加する**
  理由：package.json に書いた依存は 18 個だが、依存の依存まで含めると約 540 個入っていて、そのどれかにあとから穴が見つかる。
  手で `npm audit` を毎回実行するのは忘れるので、依存が入ってくる入口である PR で必ず調べ、穴がある状態で main に入らないようにする。

- **今の job（test）に `npm audit` のステップを 1 つ足す**
  理由：1 行で済み、CI の流れがそのまま読める。一度に足すのは 1 段にしたい。
  採らなかった選択肢：定期実行の別ワークフロー（cron と job 分けで新しい要素が 2 つ増える）。Dependabot（CI のステップではなく、PR が勝手に増える）。
  dependency-review-action（PR で新しく足した依存しか見ないので、今ある依存の穴を見逃す）。

- **`--audit-level=high` で、high 以上のときだけ落とす**
  理由：low や moderate まで落とすと、直せない軽いもので止まりやすい。
  採らなかった選択肢：オプションなし（low 以上で落ちる）。

- **dev 依存も含めて調べる**
  理由：Vitest や Playwright も CI と自分のマシンで実際に動くため。
  採らなかった選択肢：`--omit=dev`（本番に載る依存だけを調べる）。

- **`npm ci` の後ろに置く**
  理由：「インストール → 調べる」の順に読める。
  採らなかった選択肢：`npm ci` の前に置く（`npm audit` は package-lock.json だけ見るので前でも動き、早く落ちる）。

- **next と eslint-config-next を 16.3.8 に上げる**
  理由：next 16.2.0〜16.3.5 に、next/og の ImageResponse から遠隔でコードを実行される脆弱性（critical）が公開された。16.3.8 で直っている。

- **braces の脆弱性（high）は例外リストに入れて見逃す**
  理由：修正版がまだない（3.0.3 が最新）。eslint-config-next 経由で lint のときにしか使わず、読むのは自分で書いた設定のパターンだけなので、外から入力を差し込まれる経路がない。
  採らなかった選択肢：`--omit=dev`（dev 依存も調べると決めた判断を覆す）。修正版が出るまで赤のままにする（どの PR も赤になり、赤に慣れてしまう）。
  `npm audit fix --force`（eslint-config-next を 14 に下げる提案で、直すのではなく壊す）。

- **例外リストは、`npm audit --json` を読む小さなスクリプト（`scripts/audit.mjs`）で持つ**
  理由：`npm audit` 自体には例外を書く仕組みがない。依存を増やさずに済む。
  見逃した脆弱性が見つからなくなったら警告を出すので、修正版が出たときに外し忘れない。
  採らなかった選択肢：audit-ci（2024 年から更新がなく、過去に乗っ取られたことのある event-stream に依存している。脆弱性チェックのために手入れの止まった道具を足すのは本末転倒）。

## 学んだこと

- `npm audit` の「1 critical severity vulnerability」は件数の報告で、終了コードとは別物。CI が見ているのは終了コード（0 が成功、それ以外が失敗）だけ。
  終了コードは画面に出ないので `echo $?` で見る
- `npm audit --help` は使い方を表示するだけなので、終了コードは 0 になる。調べていないのに緑になる
- 緑になることだけでなく、赤になることも確かめる。脆弱性のある古いパッケージ（lodash 4.17.4）を一時的に入れて、終了コードが 1 になるのを見た
- 脆弱性には 2 種類の学びがある。個々の穴の中身（XSS、Prototype Pollution など）はセキュリティの学習。
  他人のコードの穴をどう管理するか（依存関係の管理、サプライチェーンセキュリティ）は運用の学習で、今回の CI はこちら
- 脆弱性チェックは、自分の変更と関係のない PR でも落ちる。その時点の依存と、その時点の脆弱性データベースを突き合わせるので、コードを変えなくても新しい脆弱性が公開されれば赤になる
- `npm audit fix --force` は直すとは限らない。今回はメジャーバージョンを下げる提案だった
- `braces  *` のように範囲が `*` の脆弱性は、どの版も脆弱、つまり修正版がまだないという意味
