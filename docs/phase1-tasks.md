# フェーズ 1 のやること

読み手: 自分と AI。フェーズ 1 で何をどの順に進めるかを確かめ、終わったものにチェックを付ける。
元は [learning-plan.md](./learning-plan.md) のフェーズ 1。計画が変わったらこちらも直す。

状態: 下書き

## 完了条件

6 画面が仮 API の上で動き、「ログインして習慣を作り、今日の画面に出て、詳細を見る」導線を通す E2E が CI で通る。

## 読み方

- 上から順に進める。「前提」に書いたものが終わっていれば、順番を入れ替えてよい
- 「手で書く」は、その技術で初めて書くもの。AI はコードや文書を書かず、選択肢とレビューに回る
- 1 項目がおおむね 1 PR。大きくなったら分ける
- 境界の資料（ブロック図、シーケンス図、契約、画面仕様）は冒頭に「状態（下書き / 合意済み）」を書く

## 0. フェーズ 0 を閉じる

- [ ] 依存パッケージの脆弱性チェックを CI に足す
- [ ] learning-plan.md の実績表に、フェーズ 0 の開始日、終了日、実績時間を書く

## 1. 全体の境界を決める

ほかのすべての作業の前提になる。ここが合意済みになれば、2 以降を並行して進められる。

- [ ] ブロック図を書く（手で書く）
  - ブラウザ、Next.js、仮 API、契約。フェーズ 2 以降の Go と PostgreSQL は点線で置く
- [ ] 導線 1 本のシーケンス図を書く（手で書く）
  - 前提: ブロック図
  - 画面が仮 API に何を頼むかを洗い出す。ここで出たやりとりが契約の材料になる
- [ ] 認証方式の Design Doc を書く（手で書く）
  - セッションか JWT か、Cookie の属性（HttpOnly / Secure / SameSite）、CSRF の防ぎ方
  - 背景、案の比較、決定、採らなかった案の順に書く
- [ ] API 契約（OpenAPI）を `api/` に書き、合意済みにする（手で書く）
  - 前提: シーケンス図、認証方式の Design Doc
  - 対象は 6 画面ぶん。エンドポイント、リクエスト、レスポンス、エラーの形
  - フロントの目とバックエンドの目の両方でレビューしてから「合意済み」にする

## 2. フロントの中を設計する

- [ ] クラス図を書く（手で書く）
  - 前提: 契約
  - 契約から決まる型（`User`、`Habit` など）、API 呼び出しの interface、コンポーネントの関係
- [ ] 内部設計書を書く（手で書く）
  - 前提: クラス図
  - ディレクトリの役割、依存の向き、Server / Client Component の境界、エラーと読込中の扱い、認証の確認をどこでするか

## 3. 仮 API を置く

- [ ] 最初の Route Handler を契約どおりに書く（手で書く）
  - 前提: 契約
  - 契約どおりの固定データを返すフェイク。なぜ MSW のモックではなくフェイクなのかをログに書く
- [ ] 残りのエンドポイントを足す
  - 前提: 最初の Route Handler
  - 認証まわり（ログイン、サインアップ、パスワード再設定、ログアウト）も含む

## 4. 画面を作る

各画面で、この順に進める。

1. 画面仕様を書く（.pen を読んで、表示項目、操作、遷移、状態（読込中 / 空 / エラー））
2. 観点表を書く（アクセシビリティの観点を含める）
3. コンポーネントテストを書き、赤を確かめる
4. 実装して緑にする
5. その画面の E2E を書く（コンポーネントテストとは別の PR）

## 5. セキュリティ

認証の画面と並行して学ぶ。Next.js で守れるものは実装し、Go 側で守るものは設計に書いてフェーズ 2 に渡す。

- [ ] Cookie の属性を認証方式の Design Doc どおりに設定し、テストで確かめる
- [ ] CSRF と XSS の防ぎ方を、Next.js でどう守られるかと合わせてログに書く
- [ ] パスワードの保存方法（ハッシュのアルゴリズムとコスト）を決める
- [ ] パスワード再設定トークンの扱い（有効期限、使い捨て）を決める
- [ ] レート制限とログイン試行回数の制限を決める。仮 API で試すか、設計に留めるかは着手時に決める
- [ ] 秘密情報の置き場を決める（リポジトリに置かない、環境ごとに分ける）
